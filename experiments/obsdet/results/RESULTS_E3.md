## Verdict against the predeclared bar

The bar was declared before the run. certified is material if **(1)** its total time over the natural probes at
the largest scale is ≥ 20% below smart-lex on at least one engine, or **(2)** it is ≥ 5x lower on the
LIMIT-without-total-order class (L1).

The bar is evaluated on total = preview + count, over a fixed probe set, at the largest scale (DuckDB xmax,
PostgreSQL x10).

| engine | criterion 1: certified total vs smart-lex | criterion 2: L1 smart-lex / certified | bar |
|---|---|---|---|
| DuckDB (n=986) | **4.2% lower** (95% probe-bootstrap CI −0.9% to +10.2%) | **0.96x** (CI 0.87–1.09, n=176) | **NOT MET** |
| PostgreSQL (n=962) | **86% higher**: certified is slower (CI 8.5% to 212% higher) | **0.86x** (CI 0.75–1.02, n=171) | **NOT MET** |

Secondary view, preview time only:
- DuckDB: 7.1% lower (CI −1.5% to +16.9%), L1 0.95x.
- PostgreSQL: 145% higher, L1 0.76x.
- Neither meets the bar.

**Conclusion (per the predeclared rule): no cost claim.**

What the data support is **per-probe cost parity**:
- The median per-probe smart-lex/certified ratio is 1.00x on both engines at every scale.
  - DuckDB xmax: p10–p90 0.96–1.13x.
  - PostgreSQL x10: p10–p90 0.97–1.05x.
- The totals are decided by a few heavy-tailed probes.

On PostgreSQL those tails go both ways, and both come from how the planner reacts to an index-backed tie-break
(§2):
- **Losses**: #320/#323 at 49 s vs 0.28 s; #429/#433 at ≥ 60 s vs 0.28 s.
- **Wins**: #582 at 0.07 s vs 2,592 s; #529 at 0.22 s vs ≥ 60 s.
- #582 illustrates how fragile the totals are. Its count query takes 2,596 s under every policy, so it sits in the
  timeout sensitivity set, not the main set. Replacing its 60 s lower bounds with the uncensored diagnostic values
  would move the PostgreSQL sensitivity total from 35% higher to about 43% lower. That shift comes from this one
  probe (a mis-scoped correlated subquery), so it is not evidence of a cost advantage.

## Protocol as run

- **Policies.** raw = as issued. smartlex = the existing ORDER BY keys, then every output column by position,
  NULLS LAST. certified = unchanged for DET, the certified rewrite for NARROW/ALL, and the smart-lex fallback for
  UNSUPPORTED.
- **Probes.** The 1,006 probes that have a smart-lex variant. The other 9 are multi-statement, DESCRIBE or PRAGMA.
- **Observation cost (lead's model).**
  - *Preview*: the policy's SQL with its top-level LIMIT replaced by min(L, 20). OFFSET is kept, and LIMIT 20 is
    added if absent. This is a sqlglot AST edit, done in the engine's dialect.
  - *Count*: `SELECT count(*) FROM (<raw SQL without top-level ORDER BY, LIMIT/OFFSET kept>) AS _q`. It is the
    same query for every policy.
  - *Total* = preview + count.
  - DuckDB: the 3 previews and the count run as 4 shuffled statements per repetition, and the count is charged to
    every policy.
  - PostgreSQL: each policy's observation runs as
    `BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY; preview; count; COMMIT`, with the policies shuffled. The
    total is the transaction time.
  - Each query is timed as execute + fetch in the Python client. There are 5 repetitions, and the reported value
    is the median. Timeout is 60 s (DuckDB interrupt / PostgreSQL `statement_timeout`). A timed-out or failed
    query is not repeated.
- **Engines.**
  - DuckDB 1.5.5: 8 threads, read-only files, memory_limit 12–72 GB, spill directory on node-local /tmp.
  - PostgreSQL 16.2 (pgserver wheel): one private server per job, data directory `runs/obsdet/pg/<server>_v6/`,
    UTF8 with the C collation. Identifiers are lowercased. Catalog keys are PRIMARY KEY/UNIQUE (btree), with no
    other indexes. Tables get VACUUM (FREEZE, ANALYZE).
  - PostgreSQL settings: shared_buffers 4–24 GB, work_mem 64 MB, jit off, autovacuum off. Parallelism and planner
    costs are defaults.
  - For PostgreSQL, SQL is transpiled with sqlglot 30.19 (`normalize_identifiers` for duckdb, then postgres), and
    certificates, smart-lex and previews are built in the postgres dialect.
  - All jobs ran on <CLUSTER> `<CPU_PARTITION>`, 8 cores per job, on shared nodes.
- **Scales.**
  - DuckDB: SF1, x10, xmax (x100 for 5 databases, x30 for codebase_community; cards 5.7M rows, comments 5.2M).
  - PostgreSQL: SF1 and x10, all 6 databases (codebase_community 4.0 GB, card_games 2.2 GB).
- **Probe sets, fixed across scales and policies.**
  - *Main*: succeeds at SF1, no error and no timeout at any scale.
  - *Sensitivity*: main plus probes with a timeout, where each timed-out query counts as 60 s (a lower bound).
  - Probes that fail with a deterministic error at a larger scale (18 on each engine: "more than one row returned by
    a subquery" once rows are duplicated) cannot be timed. They are excluded and listed in the analysis.
- **Classes.**
  - Probe class: ORDER BY+LIMIT, ORDER BY only, LIMIT without ORDER BY, DISTINCT, GROUP BY, other, crossed with
    the verdict.
  - L1 = LIMIT/OFFSET with verdict ≠ DET. L2 = LIMIT without ORDER BY. L3 = L1 restricted to NARROW/ALL.
- **Attribution.**
  - DuckDB: `EXPLAIN (ANALYZE, FORMAT JSON)` of every preview at xmax.
  - PostgreSQL: `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` of every preview at x10.
- **A/A checks.** Identical SQL timed as two policies (DET certified/raw; UNSUPPORTED certified/smartlex) agrees
  within 0.6% (DuckDB xmax 1.006 / 0.998; PostgreSQL x10 1.001 / 1.000).

| plan of the preview | raw | smartlex | certified |
|---|---|---|---|
| index-ordered (Limit over an Index Scan, no sort), all probes | 175 | 23 | **232** |
| incremental sort / full sort / top-N heapsort, all probes | 28 / 237 / 94 | 166 / 581 / 180 | 48 / 455 / 135 |

The certified tie-break is the primary key, which is index-backed. It turns many previews into index-ordered
scans. This is the effect guarantee G3 anticipates ("may apply, checked with EXPLAIN"). It cuts both ways:

- **Planner trap (loss).** #323 `cards c JOIN foreign_data fd ON c.uuid = fd.uuid WHERE c.watermark = 'colorpie'
  ORDER BY fd.id LIMIT 20` at x10.
  - Certified plan: `Limit → Nested Loop (Join Filter c.uuid = fd.uuid) → Index Scan using foreign_data_pkey
    (2.29M rows) × Materialize(549 cards)`. The planner expects the 20 matches early, but they are rare.
    Result: **48 s**.
  - Smart-lex plan: `Parallel Hash Join + Sort`. Result: **0.28 s**.
  - #320, #429 and #433 follow the same pattern (the last two exceed 60 s).
- **Early termination (win).** #582 `SELECT Date FROM badges WHERE UserId IN (SELECT UserId FROM users WHERE
  Location = …)`. users has no UserId column, so the subquery is correlated to `badges`.
  - Certified `ORDER BY badges.id LIMIT 20` walks the PK index and stops after 20 rows: **0.065 s**.
  - Smart-lex `ORDER BY date` must evaluate the SubPlan for every row: **2,592 s**.
  - The exact count takes **2,596 s** under every policy (diagnostic job 61874000, one uncensored run).

These are `LIMIT 20` probes over the largest tables, in three forms: `SELECT *`, three non-key columns, and three

| table | `SELECT *` | 3 columns | 3 columns + WHERE |
|---|---|---|---|
| cards | 1.7x → 1.7x | 165x → **1,174x** (123.2 vs 0.11) | 24x → **100x** (65.6 vs 0.66) |
| posts | 1.3x → 1.3x | 161x → **1,526x** (161.7 vs 0.11) | 128x → **754x** |
| comments | 1.1x → 1.1x | 202x → **1,456x** | 22x → **126x** |
| users | 1.2x → 1.2x | 82x → **342x** | 14x → **107x** |
| votes | 1.1x → 1.2x | 60x → **333x** | 1.4x → 9.7x |

Reading:

- Certified wins big when smart-lex must sort wide rows or lead with an unclustered column.
  - DuckDB: the win comes from late materialization plus dynamic-filter pruning on the clustered key.
  - PostgreSQL: certified is `Limit → Index Scan` on the PK, while smart-lex runs a parallel seq scan plus top-N
    sort.
- The win vanishes when smart-lex's first output column is itself the PK or a copy-monotone FK. Examples are
  `SELECT *` on PostgreSQL (smart-lex uses the PK index plus incremental sort) and comments/votes on DuckDB
  (zone-map pruning). There certified is at most about 1 ms slower.
- These constructed probes illustrate the mechanism. The natural agent probes rarely have this shape at a size
  where it matters.

## 5. Caveats and what is missing

- **Stress-test scales.** Replicated copies make non-key joins grow quadratically (219M rows for #71 at x100).
  They also make integer IDs and FKs monotone across copies, which helps zone-map pruning. Neither effect favours
  one policy by construction, but both shape the absolute numbers.
- **Totals are tail-dominated** on both engines. Report per-probe medians and quantiles alongside totals; do not
  quote the PostgreSQL totals without the dominance note.
- **Timeouts.**
  - DuckDB did not honour the interrupt inside the nested-loop join of #222 at x100. The job was resumed with a
    rule that skips, at xmax, the probes whose three policies all timed out at x10 (#222 only).
  - PostgreSQL `statement_timeout` is reliable.
  - Timed-out queries appear only in the sensitivity rows, counted at 60 s.
- **DuckDB raw is not a clean no-determinism baseline.** A streaming LIMIT plan can be slower than a sort (#582
  raw: 7.6 s under the pilot model).
- **Measurement.**
  - Nodes were shared, not exclusive; the A/A checks bound the paired drift at about 0.6%.
  - PostgreSQL EXPLAIN ANALYZE adds per-row timing overhead, and 2 certified EXPLAINs at x10 hit the timeout.
- **Not done.**
  - PostgreSQL at x30/x100.
  - PostgreSQL peak memory.
  - A shared snapshot for DuckDB preview + count (the data are static and read-only).
  - A mitigation for the PostgreSQL planner trap, for example making the tie-break unusable as an index order or
    capping it by cost. This is untested and noted only as a hypothesis.
- **Possible certifier inconsistency (certify.py not modified).** v6 labels 54 probes ALL with reason "key
  tie-break", and their rewrite appends a key that is not in the output, e.g. #113 `schools.cdscode` and #582
  `badges.id`. The proposal defines ALL as "only the full set of output columns completes the order". The label
  and the rewrite therefore disagree. The rewrite may be intended, but the verdict counts in E2 would then be
  mislabelled. These probes include some of the largest certified-vs-smart-lex differences (#113 on DuckDB,
  #582 on PostgreSQL).
